## Найденные баги/грабли (важно для следующих задач)
1. **pymssql + кириллица в SQL**: литералы `'Дт'`/`'Кт'` без префикса `N` приходят мусором (`'Дт'`→`'Äò'`), сравнение `== 'Дт'` всегда False → всё уходило в кредит. **Решение: `N'Дт'`/`N'Кт'`** (явный nvarchar). Проверено в `scripts/debug_encoding.py`.
2. **MSSQL не допускает подзапрос внутри агрегата**: `SUM(CASE WHEN x = (SELECT ...) ...)` → ошибка 130. **Решение**: сначала `SELECT _IDRRef FROM _Acc36 WHERE _Code='51'` в Python, потом передавать `%s` параметром.
3. **Итоги Дт/Кт считать независимо** (каждая сторона отдельно), а не классифицируя каждую строку как Дт ИЛИ Кт — строка может касаться счёта 51 с обеих сторон (разница ~304 500 за 09.2026).
4. **Поросшие процессы на порту 8080**: при рестарте сервера всегда `netstat -ano | findstr :8080` → убить именно тот PID, что LISTENING (несколько раз убивал не тот PID, и отвечал старый сервер со старым кодом — это маскировалось под «баг в запросе»).

## ⚠️ НЕЗАКРЫТЫЙ БАГ (продолжить в следующей сессии)
**Date-view API через сервер падает**: `{"error": "(402, b'The data types datetime2 and varbinary are incompatible in the greater than or equal to operator...`
- При этом **точно такой же запрос работает в standalone-скрипте** (`scripts/test_acc51_totals.py` → Дт=3 280 351,50 Кт=2 904 580,45). Код в server.py и в скрипте идентичен (6 параметров: acc51×4, db_from, db_to).
- Org-view (`sort=org`) через сервер **ещё не проверялся** — вероятно, падает так же (та же смесь bytes+str параметров).
- Гипотезы: (а) pymssql путает типы при смешанных bytes/str параметрах в одном execute; (б) сервер реально исполняет не тот код.
