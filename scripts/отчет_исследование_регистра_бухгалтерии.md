## 1. Что такое _AccRg1112

Физическая таблица MSSQL регистра бухгалтерии «Хозрасчетный». Каждая строка — одна проводка одного документа (Дебет + Кредит). Это плоский журнал всех бухгалтерских операций.

### Ключевые колонки регистра

| Колонка | Тип данных | Назначение |
|---------|-----------|------------|
| `_Period` | datetime2 | Дата/время проводки **(со сдвигом +2000 лет!)** |
| `_Active` | bit | Активная = `1`, сторнирована = `0` |
| `_AccountDtRRef` | varbinary(16) | Бинарный ID счёта по дебету → JOIN на `_Acc36._IDRRef` |
| `_AccountCtRRef` | varbinary(16) | Бинарный ID счёта по кредиту → JOIN на `_Acc36._IDRRef` |
| `_Fld1116` | float | Сумма проводки в рублях |
| `_Fld1117` | float | Валютная сумма (для валютных счетов) |
| `_Fld1122` | nvarchar | Содержание/комментарий проводки |
| `_Fld1113RRef` | varbinary(16) | Ссылка на организацию → JOIN на `_Reference150._IDRRef` |

### Критическое: сдвиг дат +2000 лет

Все даты в базе 1C хранятся со смещением **+2000 лет**. Реальная дата `2026-10-07` в базе = `4026-10-07`. Перед запросом дату нужно сдвигать, после — возвращать:

```python
DATE_SHIFT = 2000

def shift_date(date_str):   # '2026-09-29' → datetime(4026, 9, 29)
    d = datetime.strptime(date_str, '%Y-%m-%d')
    return d.replace(year=d.year + DATE_SHIFT)

def unshift_date(dt):       # datetime(4026, 9, 29) → '29.09.2026'
    return dt.replace(year=dt.year - DATE_SHIFT).strftime('%d.%m.%Y')
```

## 2. План счетов _Acc36 — как найти счёт по коду

Таблица `_Acc36` хранит все счета бухгалтерского плана:

| Колонка | Назначение |
|---------|-----------|
| `_IDRRef` | Бинарный UUID счёта (ключ для JOIN) |
| `_Code` | Код счёта строкой (`'51'`, `'62.01'`, `'62.01.10034'`) |
| `_Description` | Название счёта |

### Счёт 51 — Расчётные счета

```sql
SELECT _IDRRef, _Code, _Description FROM _Acc36 WHERE _Code = '51'
-- Результат: один счёт (родительский), IDRRef используется в WHERE регистра
```

### Группа счетов 62 — Расчёты с покупателями

Счёт 62 имеет множество подсчетов (`62.01`, `62.02` и т.д.). Для выборки ВСЕХ проводок по группе:

```sql
SELECT _IDRRef FROM _Acc36 WHERE _Code LIKE '62%'
-- Возвращает все IDRRef счетов группы 62, затем IN (...) в запросе к регистру
```

### ⚠️ Критическая ошибка при фильтрации по счёту

**Никогда не использовать подзапрос `_Acc36` внутри агрегатного запроса!** MSSQL запрещает это. Правильный паттерн: сначала получить `_IDRRef`, потом передать как параметр (или hex-строку):

```python
# ШАГ 1 — получить IDRRef счёта
cur.execute("SELECT _IDRRef FROM _Acc36 WHERE _Code = '51'")
acc51_idrref = cur.fetchone()[0]  # bytes!

h_51 = f"0x{acc51_idrref.hex().upper()}"  # "0x80DE..."

# ШАГ 2 — использовать в WHERE регистра
WHERE d._AccountDtRRef = {h_51} AND d._Active = 1
```

## 3. Главная проблема: где контрагент?

### Исходная гипотеза (НЕПРАВИЛЬНАЯ)

Первая мысль — что контрагент хранится в прямом поле регистра, как организация (`_Fld1113RRef`). Проверка показала: **такого поля нет**. В `_AccRg1112` НЕТ колонки типа `_Counterparty_RRef`.

### Почему так? Архитектура 1C Хозрасчетный

В регистре «Хозрасчетный» каждый счёт имеет назначенные **ДебетовоеСубконто** и **КредитноеСубконто**. Эти настройки определяют, какие разрезы (dimensions) заполняются для каждой стороны проводки:

- Для счёта 51 Кт-сторона → субконто = Контрагент, Банк, Договор
- Для счёта 62 Дт-сторона → аналогично

Вместо прямого поля контрагента используются **композитные информационные разрезы**:

```
Дебетовая сторона:   _KindDt{N}RRef + _ValueDt{N}_RRRef
Кредитная сторона:  _KindCt{N}RRef + _ValueCt{N}_RRRef
```

Где `{N}` — номер субконто (1, 2, 3...). Каждая пара Kind+Value хранит один разрез.

## 4. Композитные ссылки в физической БД 1C

### Структура композитной ссылки

| Колонка | Назначение |
|---------|-----------|
| `_TYPE` | Код типа данных (0x08 = ссылка, 0x05 = строка и т.д.) |
| `_RTRef` | Бинарный ID **типа** справочника (dec_id) |
| `_RRRef` | Бинарный ID **записи** в справочнике → JOIN по `._IDRRef` |

### Коды _TYPE для примитивов

| Hex-код | Тип данных | Колонка значения |
|---------|-----------|-----------------|
| 0x02 | Булево | `_L` |
| 0x03 | Число | `_N` |
| 0x04 | Дата | `_T` |
| 0x05 | Строка | `_S` |
| 0x06 | BLOB | `_B` |
| **0x08** | **Ссылка на объект** | **_RTRef + _RRRef** |
| 0x00 | Null / пусто | — |

### Алгоритм восстановления объекта из композитной ссылки

```
1. Смотрим _TYPE → если 0x08, это ссылка
2. Смотрим _RTRef → какой справочник (dec_id)
3. Смотрим _RRRef → какая запись в этом справочнике (_IDRRef)
4. JOIN: SELECT * FROM Reference{dec_id} WHERE _IDRRef = {_RRRef}
```

## 5. Как я определил, что контрагент — это Ct1 субконто

### Этап 1: Картирование колонок регистра

Скрипт `investigate_accrg1112.py` вывел полную структуру `_AccRg1112`:
- **6 Kind-колонок:** `_KindDt{1,2,3}RRef`, `_KindCt{1,2,3}RRef` (байтовые UUID)
- **6 Value колонок:** `_ValueDt{1,2,3}_RRRef`, `_ValueCt{1,2,3}_RRRef`

Вопрос: какая из этих пар хранит контрагента?

### Этап 2: Определение справочника Контрагентов

Справочник «Контрагенты» в физической БД — таблица **_Reference119** (dec_id = 119). Проверка через meta_schema.duckdb и прямые запросы к MSSQL подтвердили, что `_Description` содержит реальные названия компаний.

### Этап 3: Прямой тест JOIN для каждой Ct-колонки

Скрипт `investigate_subconto_join.py` выполнил критический эксперимент:

**Для проводок Дт=счёт 51 (все, не только Кт62):**

```sql
-- Для каждого N = 1, 2, 3 проверить JOIN с _Reference119:
SELECT COUNT(*) FROM _AccRg1112 d
INNER JOIN _Reference119 c ON d._ValueCt{N}_RRRef = c._IDRRef
WHERE d._AccountDtRRef = {idrref_51} AND d._Active=1
```

### Результаты эксперимента:

| Колонка | Совпадений с _Reference119 | Процент от всех проводок Дт51 | Вывод |
|---------|---------------------------|------------------------------|-------|
| **`_ValueCt1_RRRef`** | **9285 из 11052** | **~84%** | ✅ КОНТРАГЕНТЫ! |
| `_ValueCt2_RRRef` | ~1% (случайные совпадения) | — | Банк/МОЛ, не контрагенты |
| `_ValueCt3_RRRef` | 0% | — | Договор или пусто |

### Подтверждение: примеры из Ct1

```sql
SELECT TOP 5 c._Description, d._Period, d._Fld1116
FROM _AccRg1112 d
INNER JOIN _Reference119 c ON d._ValueCt1_RRRef = c._IDRRef
WHERE d._AccountDtRRef = {idrref_51} AND d._Active=1

-- Результат: реальные контрагенты — ООО, ИП и т.д. с суммами проводок ✓
```

## 6. Итоговая карта разрезов для Дт51-Кт62

| Разрез | Колонка в _AccRg1112 | Таблица JOIN | Доказательство |
|--------|---------------------|-------------|---------------|
| **Организация** | `_Fld1113RRef` → прямое поле | `_Reference150._IDRRef` | Работает в account51/query.py, подтверждено данными |
| **Контрагент (по Кт-стороне)** | `_ValueCt1_RRRef` — композитный разрез Ct1 | `_Reference119._IDRRef` | 84% совпадений для Дт51, скрипт investigate_subconto_join.py |
| **Банк** | `_ValueCt2_RRRef` (предположительно) | `_Reference41._IDRRef` | 1% совпадений с _Reference119 = не контрагенты; Ct2 содержит банк/МОЛ |

### Для проводок Дт51-Кт62:
- Дебет (`_AccountDtRRef`) → счёт 51 (расчётный)
- Кредит (`_AccountCtRRef`) → группа счетов 62 (покупатели)
- Контрагент на кредитной стороне счёта 62 = `_ValueCt1_RRRef`

## 7. Рабочие SQL-шаблоны

### Поступления оплаты — Дт51, Кт62 по контрагентам

```sql
-- Шаг 1: получить IDRRef счетов (в Python)
SELECT _IDRRef FROM _Acc36 WHERE _Code = '51'           -- один счёт
SELECT _IDRRef FROM _Acc36 WHERE _Code LIKE '62%'       -- группа подсчетов

-- Шаг 2: агрегация по контрагенту за период
SELECT c._Description AS counterparty,
       o._Description AS org,
       SUM(d._Fld1116)   AS total_amount,
       MAX(d._Period)    AS last_date,
       COUNT(*)          AS entry_count
FROM _AccRg1112 d
LEFT JOIN _Reference150 o ON d._Fld1113RRef = o._IDRRef      -- организация (прямое поле)
LEFT JOIN _Reference119 c ON d._ValueCt1_RRRef = c._IDRRef   -- контрагент (субконто Ct1!)
WHERE d._Active = 1
  AND d._Period >= CONVERT(datetime2, {shifted_from})
  AND d._Period < DATEADD(day, 1, CONVERT(datetime2, {shifted_to}))
  AND d._AccountDtRRef = {h_51}                    -- Дт = счёт 51
  AND d._AccountCtRRef IN ({h_62_list})            -- Кт = группа 62.xx
GROUP BY c._Description, o._Description
ORDER BY total_amount DESC                         -- или по алфавиту контрагента
```

### Сальдо/обороты счёта 51 (без разбивки по контрагенту)

```sql
SELECT организация,
  SUM(CASE WHEN _Period < date_from AND _AccountDtRRef = %s THEN _Fld1116 END) AS bal_start_dt,
  SUM(CASE WHEN _Period >= date_from AND _Period <= date_to AND _AccountCtRRef = %s THEN _Fld1116 END) AS turn_ct,
  -- ... аналогично для Дт и конечного сальдо
FROM _AccRg1112 WHERE _Active=1 GROUP BY организация
```

### Расходы (СписаниеСРасчетногоСчета — документ, не регистр!)

Для расходов используется таблица документа `_Document512`, где контрагент хранится в прямом поле:

```sql
SELECT k._Description AS kontr, SUM(d._Fld15682) AS total
FROM _Document512 d
LEFT JOIN _Reference119 k ON d._Fld15680_RRRef = k._IDRRef   -- контрагент (прямое поле!)
WHERE d._Posted = 1 AND d._Marked = 0
```

**Важно:** документы и регистр бухгалтерии — разные источники. В документах поля прямые (`_FldXXXXX_RRRef`), в регистре Хозрасчетный — через субконто (Kind+Value).

## 8. Ключевые ошибки, которых удалось избежать

| Ошибка | Почему возникает | Как избежали |
|--------|-----------------|-------------|
| `_Posted` вместо `_Active` в регистре | Документы имеют `_Posted`, но регистр — нет! | Фильтруем `d._Active = 1` |
| `_Fld1117` для суммы рублей | Это валютная сумма, всегда ≈0 для рублевых проводок | Используем `_Fld1116` |
| Подзапрос к `_Acc36` внутри агрегатного запроса | MSSQL запрещает подзапросы в SUM/CASE WHEN | Сначала получаем IDRRef отдельно, потом передаём параметром/hex-строкой |
| Даты без сдвига +2000 лет | 1C хранит даты со смещением | `shift_date()` перед запросом, `unshift_date()` после |
| Прямой JOIN контрагента через `_FldXXXXX_RRef` в регистре | Такого поля нет! Контрагент — субконто Ct1 | Используем `_ValueCt1_RRRef → _Reference119._IDRRef` |

## 10. Выводы

### Главный вывод

**Контрагент в регистре бухгалтерии _AccRg1112 хранится через композитный разрез субконто Ct1:**
- Колонка: `_ValueCt1_RRRef` → JOIN на `_Reference119._IDRRef`
- Подтверждено экспериментально: 84% проводок Дт51 успешно соединяются с реальными контрагентами

### Как это работает в архитектуре 1С

План счетов определяет для каждого счёта, какие субконто заполняются на Дебетовой и Кредитной сторонах. Для счёта 62 (Кт-сторона) первое субконто = «Контрагенты». В физической БД это разворачивается в пару колонок `_KindCt1RRef` + `_ValueCt1_RRRef`, где Kind указывает тип справочника, а Value — конкретную запись.

### Практическое применение

Все страницы дашборда (Поступления оплаты Дт51-Кт62) используют эту схему:
```python
# payment_receipts/query.py — рабочий код подтверждает правильность схемы
LEFT JOIN _Reference119 c ON d._ValueCt1_RRRef = c._IDRRef
WHERE d._AccountDtRRef = {h_51} AND d._AccountCtRRef IN ({h_62_list})
```
